## Changes made

- **Settled the single highest-risk ambiguity in the whole spec: how Docker Compose derives the project name that volume names are prefixed with.** Three independent agents flagged variants of this. Rather than trust either side of the dispute (the plan's original claim vs. a challenger's counter-claim about Compose's fallback behavior), the project name is now pinned explicitly everywhere (`-p nba-infra` / `COMPOSE_PROJECT_NAME=nba-infra`) instead of relying on implicit cwd-basename derivation. This removes the exact failure mode the whole migration exists to avoid: containers starting cleanly against silently-empty freshly-created volumes.
- **Fixed a real, confirmed bug: every post-startup verification step referenced Docker Compose v1's container-naming convention** (`nba-infra_api_1`, underscore-separated) while live investigation confirmed desktop-agent's actual containers use Compose v2's hyphenated convention (`nba-infra-api-1`). Unfixed, every exec/inspect check in the original Steps 12/14/15/16 would have failed with "no such container" on the first live run, regardless of whether the migration itself worked.
- **Fixed a verification check that would pass even on total failure.** The original data-presence check (`ls -la` + exit-code check) returns success on a completely empty directory — meaning the plan's own stated highest-impact risk (containers running against silently-empty volumes) had a verification step that couldn't actually catch it. Now checks real file counts against a source-recorded baseline.
- **Fixed a stale-snapshot bug in the volume-migration ordering.** The original sequence resumed desktop-agent's containers immediately after the local tar export, then transferred and checksummed on xps-agent afterward — during which desktop-agent was already writing new data, making the migrated snapshot stale on arrival. The sequence now delays resuming desktop-agent until after the transfer and checksum verification succeed on xps-agent, at the cost of slightly longer (still trivial) downtime.
- **Resolved a real internal contradiction**: plan.md described an operator-attended `ssh -A` agent-forwarding clone mechanism for the three sibling repos, citing unconfirmed repo visibility, while separate live investigation (done earlier in this session, via `gh repo view`) had already confirmed all four repos are public. The contradiction is now resolved in the correct direction — plain, agent-scriptable, unauthenticated `git clone` — and a new requirement pins each clone to the exact commit desktop-agent's checkout is on, since a fresh clone's branch tip isn't guaranteed to match the code that generated the migrated cache/artifact data.
- **Closed a real permission bug**: nothing added the `nba-app` service account to xps-agent's `docker` group, so every later `sudo -u nba-app docker ...` command in the original plan would have failed outright.
- **Removed real secret-exposure risk in the `.env` transfer.** The original mechanism described copying output from one terminal pane and pasting into another — displaying `BALLDONTLIE_API_KEY` on screen, in scrollback, and in the clipboard. It's now a single direct SSH-to-SSH pipe (matching the fashion-monitor migration's actual working precedent) that never displays the value. Still strictly operator-run only, never an agent tool call.

## Critiques rejected

- **Adding a systemd unit + home-infra `manifest.json` config-drift entry for this new xps-agent workload** (Design Devil's Advocate) — `manifest.json`/`drift_audit.py` belong to the separate `home-infra` repo and track home-infra's own components, not arbitrary personal apps sharing a host. Explicitly out of scope for nba-infra's own spec; noted, not built.
- **Checksum file world-readability in `/tmp` and secure-deletion of temp tar files** (Security Auditor) — the volumes hold non-secret cache/artifact data (predictor's model cache, go-feed's snapshot data), not credentials. Low value for the actual risk profile; the real secret (`.env`) already gets the full mitigation treatment.
- **A mutual-exclusion lockfile against concurrent migration runs** (Data Model Critic) — this is a one-time, single-operator manual migration, not a recurring automated job; over-engineering for the actual scope.
- **A formal resumable migration script under `docs-internal/scripts/`** (Design Devil's Advocate) — reasonable for a recurring operation, but this migration executes as a live, interactive, step-by-step session (matching the fashion-monitor migration's own successful precedent) rather than fire-and-forget tooling; noted as an option, not required.
- Steps & Sequencing Critic's original suggestion to mark the old "resume desktop containers" and "transfer to xps-agent" steps as parallelizable with each other is **superseded** by the stale-snapshot reorder above — they now have a real, intentional dependency (resume must wait for transfer+checksum to succeed), not a false one.

## Open questions requiring human input

- **No identified consumer of `desktop-agent:3020`.** Nothing in this investigation found what currently calls the desktop-agent instance (personal script, bookmark, or nothing at all). The spec now states this plainly rather than silently gliding past it: this migration stands up a verified, working parallel copy: it does not itself constitute a real cutover of any live usage. If there is a bookmark, script, or other consumer only Preston knows about, repointing it is a separate, manual action outside this migration's automatable scope.
- **AC6's exact health-check path is still approximate** (`GET /` on the api service) — the Node API's actual route table lives in the sibling `nba-analytics-hub` repo, out of this migration's scope to inspect. If a more specific health endpoint exists, the operator can substitute it at execution time; the spec's check is a reasonable default, not a hard requirement on a specific path.
